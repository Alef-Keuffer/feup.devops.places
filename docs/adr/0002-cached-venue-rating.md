# Venue Rating is cached and refreshed from Reviews, not fetched per search

Places keeps each Venue's Rating in its own database and refreshes it every five minutes from Reviews (G1) over REST, with one call to `GET /api/v1/ratings/venues`, which returns the Rating of every Venue that has reviews (G1's report, `docs/groups/2026-11-16-g1-reviews-and-ratings-report.pdf`, section 5.2.3). Search and `getVenue` read only the copy. We first planned to update the copy from a *Rating changed* message published by Reviews. On 2026-11-16 G1 told us their service works over REST only and publishes nothing (`docs/groups/2026-11-16-g1-to-g5.md`), so Places now asks for each Rating instead of being sent it. Later that day G1 offered to publish rating changes after all (`docs/groups/2026-11-16-g1-to-g5-ratings.md`), and we kept the refresh.

## Considered options

- **Ask Reviews for the Ratings on each search.** Rejected. A search with a minimum Rating would find the Venues that match its other filters, ask Reviews for the Rating of each, and drop those below the minimum in memory, so the filter couldn't be part of the SQL query that does the rest of the search. Every such search would wait on Reviews, which puts the 2-second p95 target (NFR-1) at risk, and would fail while Reviews is down (against NFR-7). Each synchronous call to another service while handling a request lowers that operation's availability (Richardson, *Microservices Patterns* §3.4.1).
- **Keep a copy, updated from *Rating changed* (our first choice).** Richardson's remedy is for a service to replicate the data it needs, kept up to date by the events that the data's owner publishes (§3.4.2). This needs Reviews to publish the message. G1 first declined, then offered it, once it had already agreed to a batch call. With the batch call we prefer the refresh. A refresh is one call every five minutes. It also corrects itself: each refresh reads every Rating again, so an answer that failed or was saved out of order is put right by the next one. A lost message, by contrast, would leave a Venue's Rating wrong until its next review, unless Reviews publishes as reliably as Places does through its outbox (ADR-0006), which we can't require of G1. All the message would add is freshness, and a five-minute lag matters little for a search filter. G1 then builds only the batch call.
- **Keep a copy, refreshed from Reviews' REST API every five minutes (chosen).** It keeps what the message gave us: search and `getVenue` answer from Places' own database whether Reviews is up or not, and the minimum Rating filter stays in the SQL query. Only the way the copy is kept current changes, and it uses the one interface G1 offers.
- **Drop the Rating from Places.** Rejected. The minimum Rating filter was our proposal, not the professor's, so we could remove it along with the Rating on a Venue, and clients would read Ratings from Reviews. Promoters would lose the filter, and the refresh is little to build.

## Consequences

- A Venue's Rating can be up to five minutes behind its latest review, which matters little for a search filter.
- A refresh is one call, whatever the number of Venues. The answer lists each Venue that has reviews, with `venueId`, `average`, `count` and `stampedAt`, as the single-Venue GET returns them. We first planned one `GET /api/v1/ratings/venues/{venueId}` per Venue, about 3 calls a second for the 1,000 Venues that NFR-1 assumes, until G1 added the batch call (question L13).
- When Reviews is down, a refresh fails and each Venue keeps the Rating it holds until the next one.
- Each entry carries `stampedAt`, by Reviews' clock, and Places replaces a Rating only with one stamped no earlier (FR-34). Two refreshes can overlap, when several copies of Places run or a refresh takes longer than five minutes, and without the rule the answer read first could be saved last and roll the Rating back.
- A Venue with no reviews is missing from the batch answer, and its single-Venue GET answers `200` with a `count` of 0 and a null `average`. A Venue also drops out of the answer when its last review is deleted, by its author or by an administrator, so a missing Venue loses the Rating Places holds. A Venue has no Rating until a refresh reads one with reviews, so a search with a minimum Rating leaves it out (FR-14).
- A missing Venue has no `stampedAt`, yet clearing its Rating must obey the same rule, or an older answer saved last could clear a Rating that a newer one set. Places stamps the clearing with the answer's HTTP `Date` header, which an origin server with a clock must send on every `2xx` answer (RFC 9110, sec. 6.6.1), so the stamp still comes from Reviews' clock. `Date` counts whole seconds, so it can fall up to a second before the moment Reviews computed its answer. If a Rating held was stamped within that second, the clearing is refused, and the next refresh clears it. We rejected two alternatives: asking G1 to list every Venue that has ever had a review, with a `count` of 0 once its reviews are gone, which costs G1 a change for a rare case; and letting a Venue keep its last Rating, which would keep a review an administrator removed in the search filter for good.
- Places calls Reviews directly, not through the Gateway, with `X-Service-Name: places`, as Events and Tickets call Places. G1 accepts this for its Rating GETs, which are read-only and public.
