> Our replies to `2026-11-16-g3-to-g5.md`: first the answers to G3's two questions, then a follow-up after reading G3's slides of 11 November (`2026-11-16-g3-tickets-and-billing-architecture.pdf`).

## Answers

**1. Is promoterId the user id?**

It will be. Right now our report only defines promoterId as "the Event's Promoter," and we copy it from the Booking request that Events (G2) sends us. Events calls us directly rather than through the Gateway, so we never see the Promoter's X-User-Id ourselves. We're defining promoterId as the Promoter's user id, the same value the Gateway sends as X-User-Id. We're asking G2 to put that id in the Booking request, not their own Promoter entity's id. Reviews (G1) needs the same thing. venueManagerId is already a user id. We'll confirm once G2 agrees.

**2. Channel and routing key**

Yes. We publish to a durable topic exchange named places, and each message's routing key is its type: BookingConfirmed or BookingCancelled. The type field also stays in the JSON body.

NOTE: One request on cancellations. Delivery is at-least-once, so a BookingConfirmed can reach you after the BookingCancelled for the same bookingId. If a BookingCancelled arrives for a bookingId you have no charge for yet, please record that Booking as cancelled. A BookingConfirmed for a cancelled bookingId should then create no charge.

## Follow-up

A follow-up to our answers, after going through your slides from 11 November:

1. Message ids. Your slides say every message has a unique id. Ours don't carry a separate one. A Booking is confirmed once and cancelled at most once, so the message type together with bookingId identifies each message. Your rule of one charge per bookingId already handles duplicates of BookingConfirmed, and cancelling an already cancelled charge changes nothing.
2. Paying the Venue Manager. You don't read venueManagerId, so as we read it, nobody pays the Venue Manager the Booking's amount. Is that out of scope for delivery 1, like paying Promoters their ticket revenue? If so, we'll list it as an open gap in our report.
