# Grilling record: answering G2's report (2026-11-16)

Goal: decide how Places answers the report of Promoters and Events (G2), `docs/groups/2026-11-16-g2-promoters-and-events-report.pdf`, which we got from G2's shared Google Doc on 2026-11-16. Their report assumed a contract with Places that differs from ours in several places. This record adds to `2026-11-14-delivery-1-report.md` and doesn't supersede it.

Vocabulary: see `GLOSSARY.md`, which gains **Rebooking**. Decisions: see ADR-0007.

## Decisions

1. **`promoterId` is the user id, and we argue it.** We ask G2 to key its Promoter by the user id rather than give it an id of its own. A separate id would only be worth having if a Promoter could be shared by several users, or if one user could hold several Promoter profiles, and G2's FR1 rules out both: "Each user corresponds to at most one promoter." What it costs: G2 resolves the user id to a `promoterId` on every command (their §4.3, first row; they accept the cost in §3.2.8), and Billing (G3) and Reviews (G1) compare `promoterId` with `X-User-Id`, so with two ids each would need G2's mapping. Keyed by the user id, the Promoter Service still says whether a user is a Promoter by whether the record exists. This answers L8 against our assumption, so we push back.
2. **Rebooking** (ADR-0007). `POST /bookings` takes an optional `replacesBookingId`. Places cancels the Event's Booking and creates the new one in one transaction, so either both happen or nothing changes. It covers postponing an Event, changing a published Event's Venue, and changing a draft Event's Venue. We rejected both cancelling then booking again, which leaves a race that ADR-0001 says only Places can close, and G2's assumed move of a Booking's days, which reverses FR-23 and needs a new message.
3. **Rules for a Rebooking:**
   - The request must name the Event's current Booking: `422 /problems/unknown-booking` if that Booking doesn't exist or belongs to another Event, and `409 /problems/booking-ended` if it has ended.
   - The old Booking doesn't count against the new days, so a postponement by one day at the same Venue works.
   - Any other rejection leaves the old Booking standing.
   - The new amount is set at today's price per day (FR-22).
   - A request without `replacesBookingId` for an Event that has a Booking stays `409 /problems/event-already-booked` (FR-19).
4. **Rebooking messages.** A Rebooking publishes *Booking cancelled* (`cancelledBy: events`) for the old Booking, then *Booking confirmed* for the new one, from one transaction through the outbox. *Booking confirmed* gains an optional `replacesBookingId`, so that Billing can tell a Rebooking from a new Booking. Otherwise a Promoter who has paid and then postpones pays twice, since Billing refunds no paid bill. Whether to carry the payment over is G3's choice. We tell G1 and G3.
5. **Whole days, and our names on the wire.** A Booking stays a run of whole days, as the professor told us ("Price per day"; "Request a place for 1 day in this period of time", `docs/notes/nov-11th-presentation-notes.md`). Events sends as `firstDay` and `lastDay` the Europe/Lisbon dates of the Event's start and end, so an Event from 20:00 to 02:00 books two days. We own `POST /bookings`, so the field names are ours (`bookingId`, `venueId`). What G2 calls things inside its own service is its business.
6. **No *Venue updated* in delivery 1.** G2 wants a `PlaceUpdated` message to refresh its copy of a Venue's name, city and capacity. We decline it. G2 already reads the Venue with `GET /venues/{venueId}` when it books, when it publishes, and when the Event's owner reads it: the safety net of its own §3.2.6. The cost: the public catalogue can show an old name and city until the owner next reads the Event, and neither group notices a capacity cut below `maxTickets`, which is where FR-21 already leaves capacity. *Venue updated* is a candidate for a later delivery.
7. **`/venues` is ours.** G2 calls `GET /places/{id}`, but the path is `GET /venues/{venueId}`. G2 put its own `/venues/{placeId}/rating` and `/venues/{placeId}/review-eligibility` there to avoid a clash with Places. We ask them to move both under a prefix the Gateway sends to G2, and we suggest no particular path.
8. **G2 must learn of a Venue Manager's cancellation.** G2's report doesn't consume *Booking cancelled*, and its Event states have none for a published Event that has lost its Venue. We point this out and ask G2 to consume *Booking cancelled*, ignoring `cancelledBy: events`. What then happens to the Event is G2's decision.
9. **Ratings from Places.** We tell G2, as an option, that our search and `GET /venues/{venueId}` already return each Venue's Rating (FR-10, ADR-0002), so `requestPlaces` needn't call G1 for each Venue.
10. **One reply.** The unsent draft to G2, sent since as `docs/groups/2026-11-16-g5-to-g2.md`, becomes our reply to G2's report. Where their report already answers one of our questions, the reply says so: *Event cancelled* carries `eventId`, and their common header carries `type` (L4, apart from the exchange name), and the reply says what we need instead for L8 and L10. Each pushback cites the section of their report it touches. A short draft to G1 and G3, `docs/groups/drafts/g5-to-g1-g3.md`, tells them about Rebooking.
11. **Events reads Venues.** `getVenue` and `searchVenues` also allow Events, called directly with `X-Service-Name: events`. G2's Event Management Service reads Venues from its own server, in `requestPlaces`, `bookPlace`, `publishEvent` and the owner's read of an Event (their §2.2, §2.3 and §3.2.6), and our endpoints table let only users, and Tickets for `getVenue`, call them, so it would have got 403.

## Still open with G2

- L4: the name of the exchange their Event messages go on. Their message names match our suggested routing key, `EventCancelled`, if they follow the broker rule.
- L8: answered against our assumption; decision 1 asks them to change it.
- L10: whether Events calls Places directly with `X-Service-Name: events`, and adopts our conventions. Their report says neither.
- New: move their `/venues` endpoints (decision 7), and consume *Booking cancelled* (decision 8).
