# Grilling record: what Places takes from the Gateway (2026-11-16)

Goal: settle what Places needs from the Gateway (G4), while reviewing our then unsent draft to G4, sent since as `docs/groups/2026-11-16-g5-to-g4.md`. The review found that Places used only one of the two roles it asked G4 for, and only once. This record adds to `2026-11-14-delivery-1-report.md` and doesn't supersede it.

Vocabulary: see `GLOSSARY.md`, whose Venue Manager is now always the Venue Manager of a particular Venue. Decisions: see ADR-0008.

## Decisions

1. **Only the user id** (ADR-0008). The Gateway forwards `X-User-Id` and nothing else; Places takes no roles. The user who submits a Venue is its Venue Manager (FR-5), and every check Places makes on a user compares the caller's id with that. This replaces the role check in decision 4 of `2026-11-14-delivery-1-report.md`, and the empty `X-User-Roles` of its "Since the session" entry on reviewing the G4 draft.
2. **Any signed-in user can list a Venue.** With no role and no approval step (FR-4), someone could list a Venue that doesn't exist, or many. We accept it for delivery 1: the role vetted no one, since we never said who grants it. Venue approval, already out of scope, is the fix for later.
3. **FR-36 and FR-38 go, and FR-37 becomes FR-36.** The report isn't delivered yet, and no message we've sent cites FR-36 to FR-38, so we renumber rather than leave gaps.
4. **`cancelledBy` keeps `venue-manager`.** G2 already has the value (`docs/groups/2026-11-16-g5-to-g2.md`), and it still says who cancelled. Only the sentence tying it to the `X-User-Roles` header goes.
5. **The questions to G4.** L11 becomes one question about the user id: does the Gateway send it in `X-User-Id` or in a signed token, and is it a UUID that never changes and is never reused? Places stores it as each Venue's Venue Manager, and Billing compares `promoterId` with it. L12 names two headers, `X-User-Id` and `X-Service-Name`. L7 asks whether the broker rule works for G4, rather than whether delivery is at-least-once, which the rule provides, not G4.
6. **Actors stay as user classes.** Promoter and Venue Manager remain the two classes of user in the Actors table, told apart by what they do, as Wiegers and Beatty's user classes are, not by a role.
7. **The G4 message**, sent since as `docs/groups/2026-11-16-g5-to-g4.md`, asks for `X-User-Id` alone, says why the id must never change, offers to check a signed token instead, and tells G4 that every path under `/venues` stays ours, since we've asked G2 to move its two endpoints there (decision 7 of `2026-11-16-g2-report.md`).

## Since the session

- 2026-11-16, G3 (`docs/groups/2026-11-16-g3-to-g5-rebooking.md`) answered our Rebooking message: "we will adapt to that".
