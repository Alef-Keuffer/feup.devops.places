## What G2's answer settles

G2 accepts everything we asked in `2026-11-16-g5-to-g2.md`:

- **L8:** the Promoter is keyed by the user id, so `promoterId` is the user id that the Gateway sends as `X-User-Id`, in the Booking request and in all of G2's messages (decision 1 of `2026-11-16-g2-report.md`).
- **Rebooking:** G2 uses `replacesBookingId` for `postponeEvent`, for `updateEvent` with a new place, and for `bookPlace` on a draft that already has a place. It checks the Venue's capacity before the request, and after a `201` it saves again rather than cancel. A postponement that keeps the same days and changes only the time sends no Rebooking, which is right: a Booking is whole days (decision 5 of that record).
- **L4:** G2's exchange is `events`, and each message's routing key is its type. The type is `EventCancelled`. The broker rule holds for G2, and the Log topic is the exchange `events`.
- **L10:** Events calls Places directly with `X-Service-Name: events`, sends `firstDay` and `lastDay` as the Europe/Lisbon dates of the Event's start and end, and adopts our conventions. Our `409` and `422` answers reach the Promoter as business errors.
- **Paths:** G2 drops `/venues/{id}/rating` and moves review-eligibility to `/events/review-eligibility`. Every path under `/venues` is ours, as we told G4.
- **Venue Manager cancellations:** Events consumes *Booking cancelled*, matched by `bookingId`, and ignores `cancelledBy: events`. A draft Event loses its Venue and stays a draft. A published Event is cancelled, and G2 publishes *Event cancelled* so that ticket holders are refunded.
- **L3:** `Room_request` becomes Booking request on the shared diagram.
- G2 accepts that there is no *Venue updated* in delivery 1, and that Venue Ratings come from our search.

## Decisions

1. **Events can read its Event's Booking: `GET /bookings?eventId={eventId}`** (G2's question a). If Events fails between our `201` and saving its Event, it doesn't know the new Booking's id, and sending the request again gets `409 /problems/event-already-booked` or `422 /problems/unknown-booking`. The new query `findEventBooking` returns the Event's Booking, with the fields of the `201` answer, as a list of at most one item. The list is empty when the Event has no Booking. A Booking that has ended is still returned, because it is still the Event's Booking. Only Events may call it, directly with `X-Service-Name: events`, as it calls `requestBooking`. A request without `eventId` gets `400`. We rejected three alternatives:
   - An `Idempotency-Key` header on `POST /bookings` needs a table of keys and their answers, and a rule for how long to keep them.
   - Answering a repeated request with the Booking it matches changes FR-19 and the Rebooking rules. It also only helps if Events still holds the exact request it sent.
   - Declining leaves an Event that holds a Booking it can't name, and so can't cancel.

   The query helps whatever Events remembers, and it lets Events check its Event against our Booking at any time, for example after a *Booking cancelled* it missed.
2. **Our answer to G2's question b is yes, with no change.** FR-26 and `handleEventCancelled` already do nothing for an Event with no Booking, or with only a Booking that has ended, and NFR-5 makes a repeated message harmless. A published Event that a Venue Manager's cancellation leaves without a Venue therefore sends us an *Event cancelled* that we drop without error. Places acknowledges the message and publishes nothing.
3. **Our reply to G2** is the draft `docs/groups/drafts/g5-to-g2-recovery.md`. It goes out now, because this record lists its edit under "For the report" (`docs/groups/drafts/README.md`).

## For the report

- Application requirements: a new requirement after FR-25: "Places shall let Events read an Event's Booking by the Event's id, and answer with no Booking when the Event has none." Add it to US-4's requirements, with a scenario:

  *Scenario: Events lost the answer.*

  | **Given** Events sent a Booking request for Event 100 and Places answered `201`, but Events failed before saving the Booking's id
  | **When** Events asks Places for Event 100's Booking
  | **Then** it gets that Booking, with its id

- System operations: a new query `findEventBooking`, with Events as its caller, US-4 and the new requirement. Its precondition is that the caller is Events, and it changes nothing. Add it to the operations table and to the Booking service's list in Services.
- REST API: add a row to the endpoints table, `GET /bookings?eventId={eventId}`, `findEventBooking`, `200`, Events. Add the note before `requestBooking` that recovers a lost `201` with it. The `400` for a missing `eventId` goes in the errors table if that table lists `400` per operation.
- `openapi.yaml`: `GET /bookings` with a required `eventId` query parameter, answering `200` with an array of Booking (at most one item), `400`, and `403` for any caller other than Events.
- Open points: L3, L4, L8 and L10 are answered as above. L4's position names the exchange `events` and the routing key `EventCancelled`.
- Messaging: the Log topic is G2's exchange `events`. *Event cancelled*'s `type` is `EventCancelled`, not "whatever value G2 chooses". The Collaborations rows for *Booking cancelled* say that Events consumes it, matched by `bookingId`.
- ADR-0007 already records decision 1 under its consequences. The report's Rebooking text that says "save again rather than cancel" adds that Events can read the new Booking with `findEventBooking`.
- The `delivery-1` row of the revision history says so.
