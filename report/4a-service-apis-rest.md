# Service APIs and collaborations

Richardson's third step defines each service's API: the operations it offers and the events it publishes [@richardson2019, sec. 2.2]^["The third step in defining the application’s architecture is to determine each service’s API." (p. 45); "The next step is to define each service’s API: its operations and events." (p. 61); "A service publishes events primarily to enable it to collaborate with other services." (p. 61)]. He first assigns each system operation to a service, then works out the collaborations between services that the operations need. Places is one service, so every operation of Table \ref{tab:operations} is Places'. Thirteen of them are requests from a user, Events or Tickets, who waits for the answer, and they are REST endpoints, described in this section. The other two start from messages, and the Messaging and collaborations section describes them with the messages Places sends.

## REST API

Places' REST API is described in one OpenAPI 3.1 document [@openapi]^["OpenAPI Specification v3.1.2 Version 3.1.2"; "The OpenAPI Specification (OAS) defines a standard, programming language-agnostic interface description for HTTP APIs, which allows both humans and computers to discover and understand the capabilities of a service without requiring access to source code, additional documentation, or inspection of network traffic."; "An OpenAPI Document is a single JSON or YAML document that conforms to the OpenAPI Specification."], `openapi.yaml` at the root of the repository, which Appendix \ref{openapi-specification} reproduces in full. Richardson names OpenAPI as the most popular language for specifying REST APIs [@richardson2019, sec. 3.2.1]^["As mentioned earlier in section 3.1, you must define your APIs using an interface definition language (IDL)." (p. 74); "The most popular REST IDL is the Open API Specification" (p. 74)]. Other groups can read the document, test against it and generate code from it, and `npx @redocly/cli lint openapi.yaml` passes with no errors (NFR-8). Each endpoint's `operationId` is the name of the system operation it implements, so the document traces back to the operations and, through them, to the requirements.

These operations are REST calls, not messages, because each caller needs the answer before it goes on. A Promoter waits for search results. Events needs to know whether Places accepted a Booking request, and at what amount, or rejected it as a conflict. And when Events sends a Rebooking, it needs to know whether its Event now holds the new Booking or still holds the old one (US-4). Richardson calls this the request/response interaction style: the caller sends a request and waits for the reply [@richardson2019, sec. 3.1.1]^["the synchronous request/response interaction style is mostly orthogonal to IPC technologies." (p. 68); "makes a request to a service and waits for a response." (p. 67)].

: The REST endpoints of Places. \label{tab:endpoints}

The endpoints are built around Places' two resources, Venues and Bookings. `GET` retrieves a representation, `POST` can create a resource, and `DELETE` requests that the server remove the resource's current association [@rfc9110, sec. 9.3]^["The GET method requests transfer of a current selected representation for the target resource."; "For example, POST is used for the following functions (among others):"; "Creating a new resource that has yet to be identified by the origin server"; "The DELETE method requests that the origin server remove the association between the target resource and its current functionality."], while `PATCH` changes some of a Venue's details. This is level 2 of the REST maturity model that Richardson describes [@richardson2019, sec. 3.2.1]^["Leonard Richardson (no relation to your author) defines a very useful maturity model for REST" (p. 74); "Level 2—A level 2 service uses HTTP verbs to perform actions: GET to retrieve, POST to create, and PUT to update." (p. 74)]. `submitVenue` and `requestBooking` answer 201 with the new Venue or Booking; the other commands return nothing, so they answer 204 with no content. Three choices need a reason.

- **Unlisting and relisting are sub-resources.** They change one aspect of a Venue, and each has its own precondition: only a Listed Venue can be unlisted, and only an Unlisted one relisted (FR-7). When an operation is hard to map to one HTTP verb, Richardson defines a sub-resource that takes a `POST`, as in his `POST /orders/{orderId}/cancel` [@richardson2019, sec. 3.2.1]^["It’s sometimes difficult to map multiple update operations to HTTP verbs." (p. 76); "One solution is to define a sub-resource for updating a particular aspect of a resource." (p. 75); "The Order Service, for example, has a POST /orders/{orderId}/cancel endpoint for cancelling orders" (p. 75)]. We rejected a `PATCH` that sets `listed` to false: `updateVenue` leaves whether the Venue is Listed unchanged, and one endpoint would then carry two operations with different preconditions.
- **A Booking request names its Venue in the body.** `POST /bookings` carries the Event, its Promoter, the Venue, and the first and last days (FR-16), which are the parameters of `requestBooking`. A Booking then has a path of its own, `/bookings/{bookingId}`, by which Events cancels it (FR-25). A Booking request for a Venue that doesn't exist (FR-17) is answered 422 rather than 404, because the path it was sent to, `/bookings`, does exist: 422 means the server understood the content type and the syntax, but could not process the instructions [@rfc9110, sec. 15.5.21]^["The 422 (Unprocessable Content) status code indicates that the server understands the content type of the request content (hence a 415 (Unsupported Media Type) status code is inappropriate), and the syntax of the request content is correct, but it was unable to process the contained instructions."]. A Rebooking is the same request with `replacesBookingId`, the Event's current Booking, which Places cancels in the transaction that creates the new one (FR-19). We rejected cancelling and then booking again: between the two requests, another Promoter's request can take the days, and the Event loses its Venue, the race the Services section keeps the calendar in Places to prevent. We rejected a `PATCH` of the Booking's days as well: it would break FR-23, need a new message for Billing, and couldn't give the Event another Venue. A `replacesBookingId` naming a Booking that doesn't exist or belongs to another Event is answered 422 for the same reason as an unknown Venue. Once Places answers 201, the old Booking is gone, so if Events then fails to save its Event, it saves again rather than cancel the new Booking. If it fails before it has the new Booking's id, it reads the Booking with `findEventBooking` (FR-38), `GET /bookings?eventId={eventId}`, which answers with a list of at most one Booking, empty when the Event has none.
- **Cancellation is a `DELETE`, answered once it is done.** Events cancels its Event's Booking by the Booking's id alone (FR-25), with `DELETE /bookings/{bookingId}`. A Venue Manager cancels a Booking under the Venue, at `DELETE /venues/{venueId}/bookings/{bookingId}`, beside the list of the Venue's Bookings they found it in (FR-28, FR-29). Who cancelled, which *Booking cancelled* reports (FR-32), follows from the endpoint, so no caller can set it wrongly. Places answers only once the Booking's days are free (FR-25, FR-31). To replace a Booking, Events sends a Rebooking rather than a cancellation, so that its Event never goes without a Venue (US-4). The optional reason is a query parameter, because content in a `DELETE` request has no generally defined meaning, and that might lead some implementations to reject the request [@rfc9110, sec. 9.3.5]^["content received in a DELETE request has no generally defined semantics, cannot alter the meaning or target of the request, and might lead some implementations to reject the request and close the connection because of its potential as a request smuggling attack"].

### Identity and access

The Gateway checks each user's token and forwards the request with the user's id (FR-35), so Places never handles tokens: authenticating requests at the edge is one of the jobs Richardson gives an API gateway [@richardson2019, ch. 8]^["Although an API gateway’s primary responsibilities are API routing and composition, it may also implement what are known as edge functions." (p. 262); "An edge function is, as the name suggests, a request-processing function implemented at the edge of an application." (p. 262); "Authentication—Verifying the identity" (p. 262)]. Events and Tickets don't go through the Gateway, which serves users. They call Places directly on the platform's network and name themselves. This is how Places tells a call from Events apart from a user's, which the System operations section left to this one. Table \ref{tab:identity} lists the two headers.

| Header | Set by | Value |
|------------------|-------------------|------------------------------------------------------|
| `X-User-Id` | The Gateway | The user's id. |
| `X-Service-Name` | Events or Tickets | `events` or `tickets`. |

: The headers that identify the caller. \label{tab:identity}

Places checks every request in three steps:

1. A request that carries neither `X-User-Id` nor `X-Service-Name` is rejected as unauthenticated, with 401 (FR-35).
2. A user calling an endpoint for Events, or a service calling one that Table \ref{tab:endpoints} doesn't allow it, is rejected as forbidden, with 403 (FR-37).
3. Where only the Venue's Venue Manager may call the endpoint, Places compares the caller's id with the Venue's Venue Manager, and rejects any other user as forbidden, with 403 (FR-36).

Places takes no roles from the Gateway. Being a Venue Manager is a relation between a user and a Venue, which Places already stores (FR-5), not a kind of user the Gateway must know about, so every check Places makes on a user compares the caller's id with the Venue's Venue Manager. Richardson leaves such checks to the service, as when the query can only be invoked by the consumer who placed the Order or by a customer service agent helping them, because a gateway can typically check only roles against URL paths, and a check on one object needs the service's domain logic [@richardson2019, ch. 11]^["The other place to implement authorization is in the services." (p. 356); "the getOrderDetails() query can only be invoked by the consumer who placed the Order (an example of instance-based security) and a customer service agent who is helping the consumer." (p. 356); "the API gateway can typically only implement role-based access to URL paths." (p. 356); "It’s generally not practical for the API gateway to implement ACLs that control access to individual domain objects, because that requires detailed knowledge of a service’s domain logic." (p. 356)]. Promoter and Venue Manager stay the two classes of user in the Actors table, told apart by the tasks they perform, as Wiegers and Beatty identify user classes, and one user can belong to both [@wiegers2013, ch. 6]^["A better way to identify user classes is to think about the tasks that various users will perform with the system." (p. 103); "An individual can belong to multiple user classes." (p. 102)]. A `venue-manager` role would have gated `submitVenue` alone, and asked G4 to decide who gets it, which nobody had said. Any user may therefore submit a Venue, and becomes its Venue Manager. Someone could list a Venue that doesn't exist, which we accept for delivery 1: Venue approval, left out of it (FR-4), is the fix for a later delivery. Places ignores any `X-User-Roles` header.

In `openapi.yaml`, the two headers are security schemes, and each operation's `security` says whether a user or which service may call it. Each operation's description also says whether the caller must be the Venue's Venue Manager.

Places trusts these headers without checking them. That is safe only because users can reach Places through the Gateway alone (NFR-10), and because the Gateway removes both headers from whatever a user sends before it sets its own. We ask G4 for both (L12). The headers still let any service inside the platform's network claim to be Events. Richardson's Access token pattern has the Gateway pass each service a token holding the user's identity and roles, and a JWT is signed so the service can check it [@richardson2019, ch. 11]^["The API gateway passes a token containing information about the user, such as their identity and their roles, to the services that it invokes." (p. 354); "One such popular standard for transparent tokens is the JSON Web Token (JWT)." (p. 356); "It’s signed with a secret that’s only known to the creator of the JWT, such as the API gateway and the recipient of the JWT, such as a service." (p. 356); "a service will perform the request operation after verifying the JWT’s signature and expiration date." (p. 357)]. We chose plain headers for delivery 1 because every group can set and read them without sharing keys. If G4 issues signed tokens, Places will check them instead, and the endpoints and the access rules stay the same.

### Conventions

We propose these conventions to every group, so that ids, days, amounts and errors mean the same in every service's API and messages (NFR-9). Table \ref{tab:conventions} gives each with its reason.

| Convention | Choice | Reason |
|--------------|--------------------------------|------------------------------------------------------|
| Ids | UUIDs. | Every group creates its own ids, and Places stores other groups' ids (the Event, the Promoter, the Venue Manager) as they store ours. A UUID needs no central registration, is intended to be unique across space and time, and can be created in a distributed system without coordination [@rfc9562]^["A UUID is 128 bits long and requires no central registration process."; "A UUID is 128 bits long and is intended to guarantee uniqueness across space and time."; "The fact that UUIDs can be used to create unique, reasonably short values in distributed systems without requiring coordination makes them a good alternative"]. Each service therefore creates ids on its own, and one group's ids are not expected to clash with another's. |
| Dates and times | ISO 8601: calendar dates such as `2027-06-06`, and timestamps with their offset from UTC, in the profile of ISO 8601 that RFC 3339 defines for Internet protocols [@rfc3339]^["This section discusses desirable qualities of date and time formats and defines a profile of ISO 8601 for use in Internet protocols."]. Our OpenAPI document marks the dates as `date` and the timestamps as `date-time`. | One text form that every language parses, that sorts as text in date order, and that can't be misread the way `06/07/2027` can, as 6 July or as June 7. |
| Time zone | A day is a whole day in the Europe/Lisbon time zone, and is sent with no zone of its own. | A day starts at a different instant in each time zone, so `2027-06-06` names the same day in every service only if they agree on one zone. Places needs it to decide what *today* is (FR-20) and when a Booking has ended (FR-30). We use Europe/Lisbon, the zone for mainland Portugal, Porto included, where the system is built. The Time Zone Database records the history of local time, and it updates daylight-saving rules when the law changes them [@tzdb]^["The Time Zone Database (often called tz or zoneinfo) contains code and data that represent the history of local time"; "It is updated periodically to reflect changes made by political bodies to time zone boundaries, UTC offsets, and daylight-saving rules."]. A named zone therefore follows the change between winter and summer time, which a fixed offset from UTC does not. |
| Money | EUR, as a decimal string with two decimals, such as `"800.00"`. | One currency, so amounts need no currency field and no conversion. A string, because software that reads JSON numbers as IEEE 754 binary64 is generally available and widely used, and those implementations approximate JSON numbers [@rfc8259, sec. 6]^["Since software that implements IEEE 754 binary64 (double precision) numbers [IEEE754] is generally available and widely used, good interoperability can be achieved by implementations that expect no more precision or range than these provide, in the sense that implementations will approximate JSON numbers within the expected precision."]. An approximated value cannot hold every two-decimal amount exactly, and Billing must receive the exact amount. |
| Errors | RFC 9457 problem details, as `application/problem+json` [@rfc9457]^["This specification's aim is to define common error formats for applications that need one so that they aren't required to define their own"; "The canonical model for problem details is a JSON [JSON] object. When serialized in a JSON document, that format is identified with the “application/problem+json” media type."]. | One error format for every service, so a caller handles errors from any group the same way. The problem's `type` tells apart rejections with the same status, such as the three conflicts of a Booking request, without parsing text. |
| API description | One OpenAPI document per service [@openapi]^["The OpenAPI Specification (OAS) defines a standard, programming language-agnostic interface description for HTTP APIs, which allows both humans and computers to discover and understand the capabilities of a service without requiring access to source code, additional documentation, or inspection of network traffic."; "An OpenAPI Document is a single JSON or YAML document that conforms to the OpenAPI Specification."]. | Every group can read the others' APIs in one format, check them with the same tools, and generate code from them. |

: The conventions we propose to every group. \label{tab:conventions}

### Errors

Every rejection that the System operations section names maps to one error response, listed in Table \ref{tab:errors}. A problem has its own `type` only where the caller may need to act on it. Every other problem has the type `about:blank`, whose `title` is the HTTP status phrase, such as "Not Found" [@rfc9457, sec. 4.2.1]^["When “about:blank” is used, the title SHOULD be the same as the recommended HTTP status phrase for that code (e.g., “Not Found” for 404, and so on)"]. The types are relative URIs that start with their full path, as RFC 9457 recommends for a type that isn't an absolute URI [@rfc9457, sec. 3.1.1]^["As a result, it is RECOMMENDED that absolute URIs be used in “type” when possible and that when relative URIs are used, they include the full path (e.g., “/types/123”)."]. They are relative because Places has no address outside the platform yet; once it has one, they can become absolute URIs under it.

| Status | Problem type | When |
|--------|-----------------------------------|----------------------------------------------------|
| 400 | `about:blank` | A parameter or the body is malformed or out of range: for instance, a search whose number of days is less than 1 or longer than its window (FR-13), or a Booking request whose last day is before its first day, or whose first day has passed (FR-20). |
| 401 | `about:blank` | The request names neither a user nor a service (FR-35). |
| 403 | `about:blank` | A user called an endpoint for Events, a service called one it isn't allowed, or the caller isn't the Venue's Venue Manager (FR-36, FR-37). |
| 404 | `about:blank` | No Venue or Booking has the id in the path, or the Booking isn't at that Venue. |
| 409 | `/problems/days-taken` | A Booking of the Venue overlaps the requested days (FR-18). |
| 409 | `/problems/event-already-booked` | The Event already has a Booking, and the request isn't a Rebooking (FR-19). |
| 409 | `/problems/venue-unlisted` | A Booking request for an Unlisted Venue, or `unlistVenue` on one (FR-7, FR-8). |
| 409 | `/problems/venue-listed` | `relistVenue` on a Listed Venue (FR-7). |
| 409 | `/problems/venue-has-bookings` | `deleteVenue` on a Venue with a Booking that has not ended (FR-9). |
| 409 | `/problems/booking-ended` | A cancellation of a Booking that has ended, or a Rebooking whose old Booking has ended (FR-30). |
| 422 | `/problems/unknown-venue` | A Booking request for a Venue that doesn't exist (FR-17). |
| 422 | `/problems/unknown-booking` | A Rebooking whose old Booking doesn't exist or belongs to another Event (FR-19). |

: The error responses of Places. \label{tab:errors}

The conflicts `days-taken` and `event-already-booked` are how Places answers when the exclusion constraint or the unique constraint of the Services section refuses a Booking. They are a normal outcome of a Booking request, which Events shows the Promoter, not an error to retry.
